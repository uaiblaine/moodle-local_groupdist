Group membership as a rule source — prototype

v2 backlog item 2, stage 1 only: an existing course group becomes a third kind of affinity rule source, beside a profile field and a cohort — the recorded use case being “keep apart the members of group Y”. The source key is group_<id> and its value is binary, exactly like a cohort's: '1' for members, empty for everyone else. The rule builder it extends is prototyped in affinity-rules.html; the preview and audit surfaces it lands in are step2-preview.html and distribution-log.html.

Status Decisions A, B and C are implemented (2026-08-21): the source key group_<id>, the bounded picker with its search web service, the self-reference gate and the visibility rule all ship as prototyped here. Decisions D and E are not. Both change how cohort rules read today — D retroactively, in the log — so they stay proposals on this page rather than riding in on a change about groups. Until D lands, a group rule inherits the cohort rendering exactly as section 4 and section 5 describe it under “today”.
Prototype Everything is interactive. Section 1 is a live builder — change a rule's type to Group, then flip its three simulation switches and watch the picker, the disabled options and the warnings change. Section 4 has two more: one puts the source group into the state the recorded use case usually produces, the other swaps every sample and quoted line in sections 4 and 5 to the decision D wording — which is still a proposal, so the “today” side of every pair is what the plugin actually renders. Every number on this page is derived from one scenario, so the two switches cannot drift apart.
Scope Groups only. Groupings are deliberately out of this round. The backlog sentence also asks for “keep together by current group in grouping X”, whose value is which group you are in — a keyed value, and a set-valued one, because {groupings_groups} has no unique constraint on (grouping, group) and a user may sit in two groups of one grouping. The allocator's value model is a single scalar per (rule, participant): clusters key on a joined string and keep-apart state keys on rule + value. A set cannot be represented without changing that model, and the change ripples into the violation vector, the contradiction scan, the audit reader and the peer-bucket keying. Stage 2 starts with that decision, not with code.

    i Every rule applies at the same time (AND). The order sets the priority: when rules conflict, or a cluster must be split for lack of seats, the rule higher up prevails and the violation is counted against the one further down — always with a warning in the preview.

    Recap (as it appears on the preview page)

    Decision A The group picker is a bounded menu up to 25 groups and a search beyond it — the same two-mode shape the cohort picker already uses, but with its own, higher limit. Why a menu at all, when cohorts are never enumerated: the never-enumerate rule for cohorts exists because cohorts are site-level and platforms carry thousands. Groups are course-bounded, this plugin's own code comments say “hundreds”, and step 1 already loads every group record of the course (groups_get_all_groups(), no limit) to validate the submitted destination ids — and reuses the same array to label the selected-group chips — so the menu costs nothing and a search-only picker would add a round trip the page does not make today. Why a limit anyway: a 200-option select is bad UI, not a security problem. 25 is deliberately the number the plugin already treats as “too many groups to show at once” (the preview's own group cap), rather than a second arbitrary constant.

    2 · The self-reference trap

    the run writes group memberships, so a group source reads what the run changes

    Picking one of the destination groups as a rule source is the one way this feature can produce a rule that provably does nothing — and today nothing would tell the teacher. With “Ignore users already in the selected groups” on (the default), every candidate who would carry the value '1' has already been filtered out of the run, so the column is empty for 100% of survivors. The rule is vacuous, and the only trace is a single warning that reads as though the data were merely incomplete:

    43 participants have no value in "Group: Group 02" and were allocated without the affinity rule.

    …where 43 is the entire candidate count. No violation, split or contradiction warning can ever name that rule, and its card in the rules report shows zero value buckets. It looks like a rule that held.

    Rejected — prevention in the picker

    Destination groups are struck from the menu while the filter is on, with the reason on the option itself. The mistake cannot be made.

    Seminar A Seminar B Lab team 2026.1 Monitors ────────────── Group 01 — a destination of this run (unavailable) Group 02 — a destination of this run (unavailable)

    Allowed — filter off, so the rule is real

    With the filter off, current members of Group 02 do take part, carry the value and the rule constrains them. It stays selectable, with a note.

    Group 02 — also a destination of this run
    Decision B Prevent it in the picker; keep a server-side error as the backstop; never reject a rule that is actually meaningful. A blanket ban would be wrong — with the ignore filter off, a destination group as a source is coherent and useful. So the gate is the conjunction: filter on and source is one of this run's destinations. The builder knows the destination ids already (it renders their names right above), so it can disable the options live and re-enable them the moment the filter is unticked — try the “Ignore users already in the selected groups” switch in section 1. The server still has to check, because the POST can be forged and because the filter can be changed after the rule was picked.
    ! The backstop needs a new message, not the existing one. Today the rule builder's only validation error is core's Data submitted is invalid, attached to a static element with an empty label — the same text for a bad shape, a duplicate source, too many rules and an unauthorised source. A self-reference rejection routed through it tells the reader nothing. Proposed:
    Rule 2 uses "Group 02", which is one of the groups this run distributes into. With "Ignore users already in the selected groups" on, none of its members take part, so the rule would have no effect. Choose another group, or turn that filter off.

    3 · Which groups may be a source

    course containment and visibility, inherited from the helper the plugin already trusts

    The offer set and the submit-side validator are the same call — groups_get_all_groups($courseid), which the plugin already uses in six places to validate destination groups. It gives course containment and per-group visibility in one step, so a group source starts from exactly the set a group destination is validated against — and decision C then subtracts one case from it, for the reason given below. Two core helpers that look right and are not: groups_get_group($id) checks neither the course nor the visibility — accepting a raw id through it turns any other course's group into a membership oracle — and groups_group_visible() tests the activity group mode, a different axis entirely.

    Decision C Only a group whose full membership the actor can already read may be a source. groups_get_all_groups() delivers almost all of that on its own — it returns an ALL-visibility group to anyone, a MEMBERS or OWN one only to a member, and a NONE one only to someone holding viewhiddengroups. Exactly one case needs an addition, and it is the row in bold above: appearing in the helper's result is not authorization to read the membership. In a MEMBERS group a member may read the whole list, so it is a sound source; in an OWN group core shows a member only their own row, so making it a source would hand them the list the group exists to withhold — a rule source is precisely a device for exposing who is in a group, since the preview paints a badge on each member. So the rule is: the helper's result, minus OWN-visibility groups, unless the actor holds viewhiddengroups — one extra predicate, stated where it is applied. Nothing is subtracted for NONE: reaching one at all already means holding the capability. Read the right-hand column as the edge case it is: viewhiddengroups is granted to teacher, editing teacher and manager by default, so for every ordinary actor nothing is hidden at all, and this whole column is reachable only through a custom role.

That is not an edge case — it is what “keep apart the members of group Y” usually means, and the pigeonhole principle decides it before the allocator does. It is also the state that produces the wording problem below, because the infeasibility warning interpolates the value and the field, and for a binary source those are the same string.

      Where “value” wording breaks on a membership source

      Three surfaces interpolate a rule's value. For a profile field the value and the label are different things (Department / Engineering). For a binary source they resolve to the same string, so each of these prints the label twice or calls a non-membership “no value”. The switch above flips the live sample; the pairs below quote the rest.

      1 · Keep-together per-group status — today

      ✓ R1 Cohort: Managers: Cohort: Managers

      Only the keep-together branch prints the value, and for a binary source it resolves to the rule's own label. This is live behaviour today, for cohorts. With a group it becomes ✓ R1 Group: Lab team 2026.1: Group: Lab team 2026.1, inside a card headed Group 01. A keep-apart rule never reaches this line — its status slot carries the repeat count instead, which is why the live sample above (rule 2, keep apart) shows no doubling.

      Proposed

      ✓ R1 Group: Lab team 2026.1: 4 members here

      For a binary source the useful number is how many of its members landed in this group. The second colon is the template's own separator between a rule's label and its status text, shared with every rule kind — so decision D changes the text, not the punctuation. The keep-apart slot is untouched, so the per-group repeat count survives.

      2 · The infeasibility warning — today

      "Group: Lab team 2026.1" (Group: Lab team 2026.1) has more participants than available groups; 8 placements repeat the value inside a group.

      Value and field are separate placeholders in the same sentence, and a binary source fills both with the same label. This is the sentence the ordinary case produces, so it is the one a teacher reads most often.

      Proposed

      "Group: Lab team 2026.1" has 12 members but only 4 groups to spread them over; 8 placements share a group.

      One sentence, one label, and it says what actually happened instead of “repeat the value”.

      3 · The “no value” counter and warning — today

      Two renderings of the same idea — the rules-report header counter and the allocator warning. Neither is missing data: those people simply are not members. For a profile field the wording flags a data-quality problem worth fixing; here it invites the reader to go and fix nothing.

      Proposed

      The second line is the only signal the vacuous-rule case of section 2 produces, which is why it has to be readable on its own.

      ! One consequence of decision D to accept deliberately. The log stores facts, but renders them through today's strings — so changing this wording changes how runs already in the log read, including every cohort run. The stored snapshot does not change and no history is lost; the sentence describing it does. That is the opposite trade from the label itself, which is frozen at apply time precisely because it cannot be recomputed.

      Two states worth drawing, because groups are deleted casually

      Source group deleted after the run — today

      Rule 2 · Group: Lab team 2026.1: value hidden from you.

      The log re-checks the source's authorization at read time, and a deleted group fails that check the same way an unauthorised one does. So the reader is told the value is being withheld from them, when in fact it no longer exists. Cohorts have the same flaw; nobody meets it, because cohorts are rarely deleted. Course groups are deleted every term.

      Proposed

      Rule 2 · Group: Lab team 2026.1 [group since deleted]

      Distinguish “gone” from “withheld”, reusing the marker the log already paints on a destination group that no longer exists. The membership facts themselves are in the snapshot and are unaffected.

      Source group deleted between step 1 and apply — today

      Notification.exception → “Data submitted is invalid”

      A rule source that stops resolving makes the preview web service throw, which the client surfaces as a raw exception toast that kills the whole preview; apply throws a full error page. Meanwhile a deleted destination group in the same run degrades gracefully — the preview re-intersects and explains itself. The harsh path is the one a teacher arriving from the group management page will hit.

      Proposed

      The group used by rule 2 no longer exists. Go back and choose the rule source again.

      Same treatment as a vanished destination: a sentence in the page, not an exception. Listed here as a consequence to confirm, not as something this feature strictly requires.

      6 · Decisions to approve, and what each one costs

      nothing below is built yet
      DecisionProposalIf rejected instead
      A · picker Bounded menu up to 25 groups, debounced search beyond, both served by groups_get_all_groups() filtered by name. Menu only — simpler, one fewer web service, unusable on a course with 200 groups.
      B · self-reference Disable destination groups in the picker while the ignore filter is on; a specific server-side error as the backstop. Warn only — the teacher can still ship a rule that provably does nothing.
      C · visibility Source set = groups_get_all_groups(), minus OWN-visibility groups for an actor without viewhiddengroups. Same call as the destination validator. Take the helper's result unchanged — a member of an OWN group could then read its whole membership off the preview.
      D · wording Membership wording instead of “value” wording on binary sources, at the five sites listed below. Also changes how cohort rules read, in the preview and retroactively in the log — which is the point, and is the one consequence to accept knowingly. Reuse the field wording — ships R1 Group: X: Group: X, a doubled infeasibility warning and “39 participants without a value” for people who are simply not members.
      E · deleted source Mark a deleted source group as deleted rather than hidden; degrade the mid-flow race like a deleted destination. Leave as is — a routine term-end deletion reads as a privacy mask, and the preview dies on a toast.
